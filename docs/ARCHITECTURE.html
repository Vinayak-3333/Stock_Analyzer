How a run gathers its data

Twice every weekday the backend pulls quotes and history for about 2,000 NSE stocks, screens them cheaply, studies the best 400 in depth, and sends you a ranked list. This page maps where each piece of data comes from, what happens to it, and where it ends up.

Where the 39 minutes go

Each block is drawn to scale. Most of the run is spent waiting on Yahoo, not computing.

How one stock is scored

Tier 2 runs this for each of the 400 shortlisted stocks. Six factor scores, each 0–100, are combined with fixed weights from core/scoring/hybrid.py.

What gets stored

Two databases on the VM. The DuckDB lake holds raw market data and per-stock history; SQLite holds one finished result set per run, which is what the dashboard and the history view read.

The feedback loop

Every score is kept so it can be checked against what the stock actually did afterwards. This is how the weights above are meant to improve.

Things the map turned up

  • Deployed 2026-10-26

    Yahoo prices are downloaded twice for the same stocks

    The stock-list step fetches 5 days for 1,698 stocks, then Tier 1 fetches a year for the same stocks. The fix fetches the year once and takes the quote from it. In a 100-stock test the quotes matched exactly.

  • Deployed 2026-10-26

    The “3-day” FII/DII flow is really one day

    The institutional score sums the last 3 days from raw_fii_dii, but only run_full_collection() writes that table, and the pipeline never calls it. On the VM the table is empty, so the code falls back to today's figure alone. Today's log shows it: FII net 888 Cr, and FII 3-day also 888. The fix stores each day's flows under NSE's trading date; the window fills over the first 3 trading days after deploy.

  • Cleanup

    Eight lake tables are never written

    They are created at startup and nothing reads or writes them. They cost nothing at runtime, but anyone reading the schema would assume options, news and macro data are being stored.
